########## 1/4  ErasureProof · 六个实验 ##########

========== A · 运行时还有没有泛型？ ==========
strings.getClass() = java.util.ArrayList
ints.getClass()    = java.util.ArrayList
是同一个 Class 对象？ true
new Box<String>() 和 new Box<Integer>() 同一个类？ true
strings instanceof List ？ true
strings.getClass() == List.class ？ false   <- 泛型接口的实参也没了，只剩实现类
结论：泛型只活在编译器眼里，运行时的对象身上一个字节都没有。

========== B · 反射看到的签名长什么样 ==========
List 接口里所有 add 方法的擦除后签名：
  add(int, Object)
  add(Object)
  getMethod("add", String.class) -> NoSuchMethodException（没有这个方法）
  getMethod("add", Object.class)  -> public abstract boolean java.util.List.add(E)
Box 类声明上的类型变量：T（边界 java.lang.Object）
Box.get 的泛型返回类型：T
Box.set 的参数类型（反射 getParameterTypes）：Object
结论：擦掉的是「使用处填的实参」，声明处的类型变量 T 以元数据形式留在 class 文件里。

B2 · 实参藏在哪：子类的 Signature 属性
  StringBox.class.getGenericSuperclass() = com.newt.java48.w02.day1.ErasureProof$Box<java.lang.String>
  从中拿到的实参 = class java.lang.String
  但 Box.set 的泛型参数类型 = T   <- 方法自己的签名里只有 T，没有 String
  StringBox 自己声明的方法数 = 0   <- 一个都没重写，实参只写在了类声明那一行
  => 想复原类型，只能「继承一个带实参的类」再读 getGenericSuperclass()：
     Spring 的 ParameterizedTypeReference、Jackson 的 TypeReference 都是这一招。


========== C · 往 List<String> 里塞 Integer ==========
塞完之后 size = 2，没有人在存的时候拦你
用 Object 接住： 42，类型是 java.lang.Integer
ClassCastException 抛在 ErasureProof.java:154  —— 就是 String s = list.get(1) 这一行
  class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')
反射 add 之后 list2 = [123]，元素运行时类型 java.lang.Integer
结论：擦除把类型检查从「运行时每个元素」搬到了「编译期每个表达式」，
      所以错误不会在写入时报，而是在「按 String 读出来」的那一刻才报 —— 报错位置和出错原因隔了好几层。

========== D · 为什么不能 new T[] ==========
(T[]) new Object[3] 的真实类型 = [Ljava.lang.Object;，放 Integer 也没事
赋给 String[] 时炸了： class [Ljava.lang.Object; cannot be cast to class [Ljava.lang.String; ([Ljava.lang.Object; and [Ljava.lang.String; are in module java.base of loader 'bootstrap')
  说明 (T[]) new Object[n] 只是骗过了编译器，数组的真实组件类型还是 Object
Array.newInstance(String.class, 3) 的真实类型 = [Ljava.lang.String;
往 String[] 里塞 Integer -> ArrayStoreException（数组的元素类型检查是运行时的）
结论：数组在运行时必须知道自己的组件类型，而擦除后的 T 什么都不剩，
      所以 new T[n] 编译不过；要造真数组，只能把 Class<T> 显式传进来。

========== E · 桥方法（bridge method）==========
StringCmp 声明的全部方法：
  compare(String, String)                       bridge=false synthetic=false
  compare(Object, Object)                       bridge=true  synthetic=true 
原因：Comparator 接口擦除后是 compare(Object, Object)，
      实现类写的是 compare(String, String)，两个签名对不上；
      编译器就补一个 compare(Object,Object) 做 checkcast 再转调 —— 这就是桥方法。
      所以反射数方法时会多出一个「你没写过」的方法，框架里遍历 method 要留意 isBridge()。

========== F · 擦除的四条硬限制（编译期就挡） ==========
  ① new T[n] / new List<String>[n]   -> generic array creation
  ② catch (T e) / new T() / T.class  -> 运行时不知道 T 是什么
  ③ void f(List<String>) + void f(List<Integer>) -> name clash: same erasure
  ④ static 成员不能用类的类型参数      -> 静态上下文里没有 this，也就没有实参
  真报错原文见 day1-result.txt 第 3/4 段（GenericLimits + GenericLimits2）

========== 收尾 ==========
一句话：擦除擦掉的是「实参」，留下的是「声明」，代价是运行时无法复原类型。

########## 2/4  PecsDemo · 五个实验 ##########

========== A · 泛型是不变的（invariant） ==========
List<Object> objs = strs;  编译错误：incompatible types
  （不是设计缺陷，是故意的：数组协变留下的坑，泛型用不变性补上）
对比：Object[] arr = new String[2]; arr[0] = 42; -> ArrayStoreException（运行时才发现）
复制一份之后 copied = [a, b, 42]，strs 仍然是 [a, b]

========== B · ? extends Number：只读 ==========
sum(List<Integer>) = 6.0
sum(List<Double>)  = 4.0
sum(List<Long>)    = 30.0
  签名是 sum(List<? extends Number>)，一个方法吃掉三种 List
读出来 1，静态类型 Number，实际 Integer
wild.add(null) 允许（null 是唯一对所有子类型都合法的值），size = 4
wild.add(4) 编译错误：? extends Number 可能是 Double，编译器不敢让你写
结论：extends 通配符 = 生产者，只能读；读出来的上界就是那个上界类型。

========== C · ? super Integer：只写 ==========
fill 到 List<Object>  -> [0, 1, 2]  元素实际类型 Integer
fill 到 List<Number>  -> [0, 1, 2]
fill 到 List<Integer> -> [0, 1, 2]
  签名是 fill(List<? super Integer>, int)，三种容器都能收
wild.add(7) 可以，nums 变成 [0, 1, 2, 7]；读出来静态类型只能是 Object -> 7（运行时是 Integer）
Integer bad = wild.get(0) 编译错误：容器可能是 List<Object>，里面不一定装 Integer
结论：super 通配符 = 消费者，只能写；读出来只能当 Object。

========== D · Collections.copy 的签名为什么长那样 ==========
copy(List<Object> dest, List<String> src) 之后 dest = [a, b, c]
  签名：<T> void copy(List<? super T> dest, List<? extends T> src)
  dest 是消费者 -> super；src 是生产者 -> extends；T 由两边共同推断出来

========== E · Stack 的 pushAll / popAll ==========
pushAll(List<Integer>) + pushAll(List<Double>) 之后 size = 5
popAll 到 Collection<Object> -> [2.5, 1.5, 3, 2, 1]
换成 Collection<Integer> 接 popAll 会编译错：栈里可能有 Double

========== 收尾 ==========
PECS：参数是「生产者」用 extends（只读），是「消费者」用 super（只写）。
没有通配符的 <T> 只能保证「进和出是同一种类型」，一旦要跨类型传，就得放开一端。

########## 3/4  WildcardCapture · 通配符捕获（Day 1 遗留补齐） ##########

========== A · 直接对 List<?> 交换，编译不过 ==========
  能想到的最自然写法：
    void swapBad(List<?> xs, int i, int j) {
        Object tmp = xs.get(i);
        xs.set(i, xs.get(j));   // <- 编译错误
        xs.set(j, tmp);         // <- 编译错误
    }
  javac -Xdiags:verbose 的原话（实测，不是想象）：
    error: method set in interface List<E> cannot be applied to given types;
      required: int,CAP#1
      found:    int,CAP#2
      reason: argument mismatch; Object cannot be converted to CAP#1
      where CAP#1,CAP#2 are fresh type-variables:
        CAP#1 extends Object from capture of ?
        CAP#2 extends Object from capture of ?
  关键就在 required CAP#1 / found CAP#2：同一句里的两个 ? 各自独立捕获，
  编译器没有依据认为 CAP#1 和 CAP#2 是同一个类型，而 set 要求「和 get 出来的那个一致」。
  第二行 xs.set(j, tmp) 的报错是 found: int,Object —— tmp 的静态类型是 Object，
  同样不是 CAP#1。所以两个 ? 的容器，连「读出来再放回去」都做不到。

========== B · 正例：helper 方法把 ? 捕获成 T ==========
swapWild(List<Integer>, 0, 4) -> [5, 2, 3, 4, 1]
  入口签名仍是 List<?>，里面转调 swap(List<T>)：
  T 被推断成「那个 ? 捕获出来的 CAP#1」，整个方法体内 T 是同一个类型，set 就合法了。
reverseWild(List<String>) -> [d, c, b, a]
  交换之后 ints.get(0) 仍然是 Integer -> Integer

========== C · JDK 17 自己怎么写的 ==========
  java.util.Collections:495-502（JDK 17 src.zip 原文）：
    @SuppressWarnings({"rawtypes", "unchecked"})
    public static void swap(List<?> list, int i, int j) {
        // instead of using a raw type here, it's possible to capture
        // the wildcard but it will require a call to a supplementary
        // private method
        final List l = list;
        l.set(i, l.set(j, l.get(i)));
    }
  两个结论：
  ① 捕获不是唯一解，JDK 明确知道「捕获要多一个私有方法」，选了 raw type + 压制警告；
  ② 它把 raw 的作用范围压到 3 行内（final List l = list 之后就再没碰过 list），
     这是 raw type 唯一可以接受的用法 —— 局部、短、有注释、有 @SuppressWarnings。
  Collections.swap(List<Integer>, 0, 2) -> [9, 8, 7]（行为与 B 段一致）

========== D · raw type 的代价：错误被推迟到读出来 ==========
  raw.set(0, "我不是 Integer") 编译通过，容器里现在混了一个 String
  容器内容 = [我不是 Integer, 2, 3]
  按 Integer 读出来 -> ClassCastException: class java.lang.String cannot be cast to class java.lang.Integer (java.lang.String and java.lang.Integer are in module java.base of loader 'bootstrap')
  和 Day 1 C 段同一个病：错误现场（get）离肇事现场（raw.set）隔了好几层。
  所以 helper 捕获不只是「少个警告」，它把 checkcast 之外的类型约束也保住了。
  Map<?, ?> 读 entrySet -> [a=1]；但 wild.put("b", 2) 编译不过（key 和 value 都是捕获类型）

========== 收尾 ==========
通配符捕获 = 编译器给这个 ? 起个临时名字（CAP#1）。但捕获发生在「每次方法调用」上：
同一个 List<?> 在同一句里调 get 和 set，各捕各的（CAP#1 / CAP#2），
所以「get 出来的那个」塞不回「要求 CAP#1 的 set」。把签名换成 <T> 之后，
T 在方法体里只推断一次，全程同一个类型，才写得下去。
