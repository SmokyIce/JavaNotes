【HashMapBuAnQuan 实测记录 — JDK 17.0.12，Windows】
配置：8 线程 × 每线程 5000 个 key（区间互不重叠）→ 应放入 40000
说明：size 是 HashMap 自己的计数器；实际节点数是遍历 entrySet 真数出来的。

—— 第 1 次 ——
应放入             : 40000
HashMap 报的 size  : 23771
实际遍历节点数     : 36613
【真实丢的数据】   : 3387
【计数器偏差】     : +12842  → size 少算（数据进去了，++size 没算上）

—— 第 2 次 ——
应放入             : 40000
HashMap 报的 size  : 27481
实际遍历节点数     : 28869
【真实丢的数据】   : 11131
【计数器偏差】     : +1388   → size 少算（同上）

—— 第 3 次 ——
应放入             : 40000
HashMap 报的 size  : 24244
实际遍历节点数     : 22218
【真实丢的数据】   : 17782
【计数器偏差】     : -2026   → size 多算（数据被覆盖了，++size 还是加了）

—— 对照组：换成 ConcurrentHashMap（同样 8 × 5000）——
应放入 = 40000    实际 = 40000    丢了 = 0

【结论】
1. size 和真实数据是两个独立的量，**两个方向都会偏**：
   · 偏差为正（size 少算）→ 数据进去了，但 ++size 撞车丢了增量
   · 偏差为负（size 多算）→ 两个线程写同一个空桶，数据被覆盖，但 ++size 都成功了
2. 三次实测中，真实丢的数据分别是 3387 / 11131 / 17782 —— 数据丢失多少也不稳定。
3. 所以「size 变小」和「数据变少」**不是一回事**，不能互相推断。
   唯一可靠的判断方式：遍历一遍，真的数节点。
