【HashMapBuAnQuan 实测记录 — JDK 17.0.12，Windows】
配置：8 线程 × 每线程 5000 个 key（区间互不重叠）→ 应放入 40000
说明：size 是 HashMap 自己的计数器；实际节点数是遍历 entrySet 真数出来的。

================================================================
一、size vs 真实数据（跑三次）
================================================================

—— 第 1 次 ——
应放入             : 40000
HashMap 报的 size  : 23771
实际遍历节点数     : 36613
【真实丢的数据】   : 3387
【计数器偏差】     : +12842  → size 少算（数据进去了，++size 没算上）

—— 第 2 次 ——
应放入             : 40000
HashMap 报的 size  : 27481
实际遍历节点数     : 28869
【真实丢的数据】   : 11131
【计数器偏差】     : +1388   → size 少算（同上）

—— 第 3 次 ——
应放入             : 40000
HashMap 报的 size  : 24244
实际遍历节点数     : 22218
【真实丢的数据】   : 17782
【计数器偏差】     : -2026   → size 多算（数据被覆盖了，++size 还是加了）

—— 对照组：换成 ConcurrentHashMap（同样 8 × 5000）——
应放入 = 40000    实际 = 40000    丢了 = 0

结论：
1. size 和真实数据是两个独立的量，**两个方向都会偏**。
2. 所以「size 变小」和「数据变少」不是一回事，不能互相推断。
   唯一可靠的判断方式：遍历一遍，真的数节点。

================================================================
二、成环检测（跑 13 次）
================================================================
11 次    无环，但数据照样丢一万多
 1 次    检出 2 个桶成环
 1 次    直接死循环，只能超时杀掉进程

约 15% 的概率踩到结构损坏。

【为什么 JDK 8 还会成环】
JDK 8 修掉的是 JDK 7 那个「必然发生」的自环（头插 → 尾插 + 显式断尾，单线程下不出错）。
但 resize() 里 table = newTab 是在**搬运之前**执行的：

    Node<K,V>[] newTab = (Node<K,V>[])new Node[newCap];
    table = newTab;          // ← 先挂上去
    if (oldTab != null) { ... 才开始搬运 ... }

两个线程同时 resize 时：
    A: oldTabA = T0(16) → newTabA = Node[32] → table = newTabA
    B: 读 table 拿到的却是 newTabA（A 刚挂上的）
       → oldTabB = newTabA → newTabB = Node[64] → table = newTabB
于是 A 在往 newTabA 写，B 却把 newTabA 当「源」在读，还顺手改 next 指针
→ 同一条链表被一边写一边读，交错就能拼出环。

准确说法：JDK 8 把成环从「必然」降成了「偶发」，但没有消除。

================================================================
三、第三类故障：并发树化导致 ClassCastException
================================================================
最严重的一次：8 个线程**全部**抛异常退出，40000 条只进去 1542 条。

java.lang.ClassCastException: class java.util.HashMap$Node
    cannot be cast to class java.util.HashMap$TreeNode
    at java.util.HashMap$TreeNode.moveRootToFront(HashMap.java:1986)
    at java.util.HashMap$TreeNode.putTreeVal(HashMap.java:2165)
    at java.util.HashMap.putVal(HashMap.java:636)
    at java.util.HashMap.put(HashMap.java:610)

原因：桶内链表到 8 个会把 Node 换成 TreeNode，
但另一个线程可能正好在这个桶里 put，读到「半转换」的状态，强转就炸了。

================================================================
四、三类故障汇总
================================================================
| 故障             | 表现                              | 频率            |
| :--------------- | :-------------------------------- | :-------------- |
| 数据丢失 / size 错 | 静默，最难发现                     | 几乎每次        |
| 成环             | get()/put() 死循环，CPU 100%       | 约 15%          |
| 并发树化          | ClassCastException，线程直接崩      | 偶发，一崩全崩   |

结论：HashMap 任何并发场景都不能用，一律 ConcurrentHashMap。
