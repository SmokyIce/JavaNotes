两个触发条件的区别：
  · size 触发：元素总数超了容量承载能力 → 整表翻倍（16→32→64→128…）
  · 链表触发：个别桶太挤，但容量还不到 64 → 也翻倍（可避免过早树化）
  两条路走的都是同一个 resize()，所以容量永远是 2 的幂。

========== 实验 C：容量的天花板在哪 ==========
  HashMap.MAXIMUM_CAPACITY = 1073741824   （就是 1 << 30 = 1073741824，约 10.7 亿）

  传入的初始容量     →  实际容量（threshold 里存的值）
  100                →  128
  1000               →  1024
  1048576            →  1048576
  1073741823         →  1073741824
  1073741824         →  1073741824
  2147483647         →  1073741824

  为什么不是 2^32？也不是 2^31 - 1？
    · 容量必须是 2 的幂，候选只有 2^30 / 2^31 / 2^32 …
    · 桶数组的长度是 int，而 1 << 31 = Integer.MIN_VALUE（负数），当不了长度
    · 所以 2 的幂里最大的安全值就是 1 << 30 = 1073741824
    · 到顶之后 resize() 会把 threshold 设成 Integer.MAX_VALUE，从此不再扩容

  还有个现实约束：2^30 个引用 ≈ 4 GB（压缩指针）～ 8 GB，普通机器分配不出来。

  顺带一个细节：容量到 2^30 时，n-1 = 0b0111...1111（30 个 1），
                只用到 hash 的低 30 位 —— hash 的最高 2 位永远闲置。
