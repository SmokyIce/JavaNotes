  private static volatile com.newt.java48.w03.day3.DclSingleton$Singleton safe;
    descriptor: Lcom/newt/java48/w03/day3/DclSingleton$Singleton;

④ 构造里的写顺序（DCL 半初始化的现场）
$ javap -p -c -cp out 'com.newt.java48.w03.day3.DclSingleton$Singleton'
--------------------------------------------------------------
  void init(java.lang.String);
    Code:
       0: aload_0
       1: iconst_1
       2: putfield      #16                 // Field a:I
       5: ldc2_w        #20                 // long 2l
       8: invokestatic  #22                 // Method com/newt/java48/w03/day3/DclSingleton.sleep:(J)V
      11: aload_0
      12: aload_1
      13: putfield      #28                 // Field b:Ljava/lang/String;
      16: aload_0
      17: ldc2_w        #32                 // long 99l
      20: putfield      #34                 // Field c:J
      23: return

  要点：putfield a → invokestatic sleep → putfield b → putfield c。
        字节码看不出「putstatic 被提前」—— 那是 JIT/CPU 的事，字节码层面永远是这个顺序。
        所以「看字节码验证 DCL 有 bug」这条路走不通，只能靠 JMM 的规则推。

⑤ 反汇编：StoreLoad 屏障真的在
$ java -XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly -cp out com.newt.java48.w03.day3.DclSingleton
--------------------------------------------------------------
  全文 lock 前缀（f0）出现次数： 21 处
  原文样例（volatile 写后面的那道屏障）：
      0x00000219877fdf9c: f083 4424 | c000 488b | d049 33d1 | 48c1 ea15 | 4883 fa00 | 0f85 c707 
      0x000002198f2d1830: 4d8b 5740 | 4d8b 5f50 | f083 4424 | c000 4180 | 3800 0f84 | 13ff ffff | 4588 204d 

  解码：f0 = LOCK 前缀，83 44 24 c0 00 = addl $0x0,-0x40(%rsp)
        整条就是 lock addl $0x0,-0x40(%rsp) —— HotSpot 在 x86 上实现 StoreLoad 屏障的标准做法。
        （本机 PrintAssembly 只输出十六进制、不带助记符：没有 hsdis 解码器。
          所以上面的「解码」是我按 x86 编码表读的，不是工具给的。）

  另一半：volatile 读不加任何指令。x86 的 TSO 天然不允许 LoadLoad / LoadStore 重排，
  所以读侧只需要编译器别把读提到前面，硬件不用管。
