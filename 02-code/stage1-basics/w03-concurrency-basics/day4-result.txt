========== A · wait() 不写在 synchronized 里会怎样 ==========
  wait()   → IllegalMonitorStateException: current thread is not owner
  notify() → IllegalMonitorStateException: current thread is not owner
  → 两个方法都要先「拥有这个对象的 monitor」，也就是必须写在 synchronized(any) 里。
  → 原因不是语法洁癖：wait 要做的三件事（释放锁 → 挂起 → 被唤醒后重新抢锁）
     全都得围绕 monitor 完成，没有 monitor 就没有「要释放的东西」。

========== B · 被唤醒 ≠ 条件成立：if 只查一次，while 会重查 ==========
B1 两个消费者 wait() + 生产者放 1 件货 + notifyAll()（用 if）
    [生产者] 放入 7，notifyAll() 把所有等待者都叫醒
    [消费者1] ✓ 取到 7
    [消费者2] ✗ 醒了就往下走，货架是空的 —— 这就是 if 的漏洞
    → 空手而归（取到 null）1 次
    → 这就是无数生产者-消费者写错的地方：notifyAll 叫醒了 2 个人，货只有 1 件

B2 同样场景，把 if 换成 while
    [生产者] 放入 7，notifyAll() 把所有等待者都叫醒
    [消费者1] ✓ 取到 7
    [消费者2] 醒来后重查：还是空的 → 接着 wait()
    [消费者2] 货架已关闭，空闲退出
    → 空手而归 0 次；「醒来重查又回去等」1 次
    → 结论：wait() 必须包在 while(条件不成立) 里。被叫醒只是「有机会了」，不是「条件成立了」。
    → 真正的虚假唤醒由 JVM/OS 发起，无法主动触发；但后果与上面这个场景一模一样。

========== C · notify() 一次只叫醒一个 ==========
C1 放 2 件货 + notify()    一次 → 取走 1 件，剩 1 件，还有 1 个消费者停在 WAITING
C2 放 2 件货 + notifyAll() 一次 → 取走 2 件，剩 0 件，还有 0 个消费者停在 WAITING
  → notify() 唤醒的是「任意一个」等待者，一次就一个。
  → 放了几件货、变更了几种条件，就得喊几声 —— 而真实业务里这个「几声」根本算不准，
     所以默认用 notifyAll()：多叫醒几个人只是多几次空转，少叫醒一个是永久的卡死。
C3 没人在等时 notify() 一次，随后的 wait(200) 等了 201 ms 才超时返回
  → monitor 不是信号量，notify 不是一个会累加的计数。它只是「当场叫醒」这个动作。
  → 所以「先改条件再 wait」一定会丢 —— 条件与 wait 必须在同一把锁里检查。

========== D · wait() 会释放锁，sleep() 不会 ==========
  持锁者 sleep(500): 另一个人排队 414 ms 才进临界区
  持锁者 wait(500) : 另一个人排队   0 ms 才进临界区
  → 同是「停 500 ms」，一个把门锁着睡，一个把钥匙放桌上。
  → 所以「在 synchronized 里 sleep」是并发性能的头号杀手；要让出锁，只能靠 wait。

========== E · 中断打断 wait()：抛异常的同时清掉中断标志 ==========
  E1 打断前 isInterrupted          = false
  E2 抛了 InterruptedException     = true
  E3 捕获后 isInterrupted 还是 true = false
  → 抛 InterruptedException 时 JVM 会先清标志，所以捕获后必须自己再 interrupt() 一次，
     否则上层永远不知道「有人想让我停」。
  → 另外 wait(0) 是「永久等待」，不是「等 0 毫秒」—— 超时参数 0 表示无限。

========== A · 对拍：10 线程 200 万次自增，一次都不能丢 ==========
  用简易 AQS 上锁：期望 2000000，实际 2000000，丢 0，耗时 730 ms
  对照（不锁）  ：期望 2000000，实际 448209，丢 1551791，耗时 26 ms
  → lock()/unlock() 前后各有内存屏障，所以临界区里的普通 int 也是安全的。

========== B · 重入：state 就是重入次数 ==========
  lock() 一次            → state = 1
  再 lock() 两次         → state = 3（同一个线程，计数累加）
  unlock() 两次          → state = 1（还剩一层，锁没真放）
  unlock() 第三次        → state = 0（这时才真的放锁）
  再多 unlock() 一次     → IllegalMonitorStateException: current thread is not owner
  → 这就是为什么必须 try/finally：重入计数少减一次，锁就永远放不掉。

========== C · 三种锁，两种临界区长度（同一套脚手架） ==========
  临界区                      synchronized  ReentrantLock       简易 AQS        简易÷内置
  ≈1 ns（200 万次）               118 ms           50 ms        687 ms        5.8 倍
  ≈0.5µs（5 万次）               84 ms           75 ms         95 ms       1.13 倍
  → 临界区一拉长，5~6 倍缩到 1 倍附近：park 的代价是固定的几微秒，
     临界区越长摊得越薄；而临界区只有 1 ns 时，谁少挂起一次谁赢 —— 这正是 ReentrantLock 猛自旋的原因。
  → 所以「手写版慢 5 倍多」不是队列写错了，是这个负载在考「自旋 vs 挂起」的取舍。
  → 数字只用于横向比较（三轮取最小），不是 JMH 基准。

========== D · 队列的真实开销：两次 CAS 与 park ==========
  本轮耗时 729 ms
  CAS 建哨兵（head）1 次 —— 队列惰性初始化，整个进程只建一次
  CAS 抢尾（tail）  87742 次 —— 平均每 23 次加锁 1 次
  park 挂起         175075 次 —— 平均每 11 次加锁挂起一次
  醒来但没抢到      87500 次
  → 总耗时 ÷ 挂起次数 = 4.2 µs/次：这就是「挂起比自旋贵几个数量级」的实数
  → 入队两次 CAS 的必要性：哨兵 1 次 + 每次真正入队 1 次。
     两个状态转移各自必须原子，合并成一个 CAS 做不到（要同时改 head 和 tail）。
  → 「醒来没抢到」> 0，就是 park 之后必须重试的实测证据：这些线程被 unpark 了，
     但锁已经被别人拿走 —— 最常见的是「刚 unlock 的那个线程转头又 lock」，
     在压测循环里它就是最凶的插队者。不重查就会带着「我以为我有锁」继续跑，临界区直接失效。

========== A · 公平锁 vs 非公平锁（8 线程 × 20000 次） ==========
  模式                   耗时         连续抢到次数          单线程最长等待
  非公平              30 ms       154582 次          387 µs
  公平             1228 ms          445 次          582 µs
  → 非公平快 40.9 倍；连续抢到 154582 次 vs 445 次。
  → 「连续抢到」= 同一个线程 unlock 之后立刻又 lock 成功。
     非公平锁允许它直接插队（barging），公平锁必须先去队尾排队，所以这个数接近 0。
  → 注意「最长等待」这一列：公平锁反而更大（582 µs vs 387 µs），这和「公平锁不会饿死人」的直觉是反的。
     原因是临界区只有 1 ns，公平锁等的主要不是临界区，而是「解锁后唤醒下一个人」的交接成本（几 µs）；
     排 8 个人就是 8 次交接。非公平锁靠自旋，反而几乎不用走内核。
  → 所以公平换来的不是「等得更短」，是「等得有上界、可预测」：
     最坏情况 = 排在你前面的人数 × 交接成本；而非公平的理论最坏情况是无穷（可以被一直插队）。

========== B · Condition 精确唤醒 vs notifyAll 全员广播 ==========
  4 生产者 + 4 消费者，队列容量 1，共 8000 件货
  实现                     耗时           无效唤醒
  Condition         143 ms           11 次
  wait/notifyAll      172 ms         7666 次
  → 「无效唤醒」= 醒来一看条件还是不成立，只能再睡回去的次数。
     Condition 版 11 次，notifyAll 版 7666 次，差 697 倍。
  → 差距来自「唤醒谁」：Condition 有两个等待队列，signal 只叫非空队列里的一个；
     synchronized 只有一个等待集合，notifyAll 把消费者和生产者一起叫醒，绝大多数醒了也白醒。
  → 这就是 Condition 存在的唯一理由：把「等同一个条件的线程」分组成多个队列。
