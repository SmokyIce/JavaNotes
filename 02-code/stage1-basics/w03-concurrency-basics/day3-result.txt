========== A · 程序次序规则：先写后读，内存看来能不能反过来 ==========
  100000 轮：(r1,r2)=(0,0) → 42944 次 / (1,1) → 0 次 / 只有 r1=1 → 27579 次 / 只有 r2=1 → 29477 次
  (1,1) 的含义：两个线程都看见了对方的写 —— 这才是「真的重叠执行」的轮次。
  (0,0) 的含义：两个读都发生在对方写之前 —— 只有在写进 store buffer、读直接走时才会出现。
  → 测到了 (0,0)：`ar1 = ay` 被提到了 `ax = 1` 之前。程序次序只约束单线程内部。
    对照：(1,1) 与 (0,0) 的关系正是「可见性」这个词的全部含义。

========== B · monitor 规则：synchronized 不只管互斥，还管可见性 ==========
  [B1 有 monitor] 看见标志？true，自旋 11704110 次，读到的 data = 42
    → data 不是 volatile，可见性是「写线程解锁 → 读线程加锁」这条 HB 边传过来的。
      更硬的证据是它「没被优化掉」：同样的自旋循环放进 synchronized 里，
      JIT 不敢把 bFlag 的读提到循环外（monitor 是一道屏障）；见 C1 的对照。
    （第一版我在循环体里放了 System.nanoTime() 当超时判据 —— 方法调用挡住了 JIT 提升，
      测出 true 还以为是结论。改成纯自旋 + 写线程先睡 80 ms，C1 才复现出失败。）

========== C · volatile 规则：发布 / 订阅 ==========
    第 1 轮：看见？false，自旋 1500000000 次
    第 2 轮：看见？false，自旋 1500000000 次
    第 3 轮：看见？false，自旋 1500000000 次
    第 4 轮：看见？false，自旋 1500000000 次
    第 5 轮：看见？false，自旋 1500000000 次
  [C1 普通标志] 5 轮：看见标志 0 轮，其中「标志到了但数据没到」0 轮
  [C2 volatile 标志] 5 轮：看见标志 5 轮，其中数据不完整 0 轮，平均自旋 295306602 次
  → C1 与 C2 只差一个 volatile：前者撞满上限永远看不见，后者 80 ms 后立刻看见。
    「看见之后数据是否完整」在 x86 上测不出差异（TSO 不重排 store-store），
    但 volatile 的 HB 保证的是两件事一起：标志可见 + 标志之前的写也可见。
    这也是 DCL 敢靠 volatile 的理论依据 —— 换 ARM 就会真的出现「标志到了、数据没到」。

========== D · 启动与终止规则：start() 与 join() 是两条屏障 ==========
  [D1 start 前写] 子线程读到 777（期望 777）
  [D2 不 join] 500 轮：读到 0（还没算完）160 轮，读到结果 340 轮
  [D3 有 join] 500 轮：拿到完整结果 500 轮（期望 4951）
  → start() 让「之前的写」对新线程可见；join() 让「线程内的写」对调用者可见。
    D2 读到 0 不是「线程没跑」，是「你比它先读」—— 抢跑，不是并发 bug，但一样错。

========== E · volatile 写到底贵在哪（6 轮取最小值，丢第 1 轮预热） ==========
  普通字段写     0.40 ms（0.020 ns/次）← 被 JIT 消掉了，只留最后一次 store
  lazySet()      2.67 ms（0.133 ns/次）← 有序写，不加 lock 前缀
  set()         15.45 ms（0.773 ns/次）← volatile 写
  → set() 是 lazySet() 的 5.8 倍。差的不是指令条数（字节码都是 putfield），
    是 x86 上跟在 volatile 写后面那条 `lock addl $0,(%rsp)`（StoreLoad 屏障）。
    普通写那行的 0.0x ns 是**测量事故**：JIT 发现中间值没人看，整个循环只剩最后一次写。
    「数字接近 0 就是没测到」，这条今天又踩了一次。

========== D1/D2 · 压力测试：不加 volatile vs 加 volatile ==========
  [D1 无 volatile] 50 轮 × 6 线程（每轮抢 30 ms）：拿到构造没跑完的对象 0 次
  [D2 有 volatile] 50 轮 × 6 线程（每轮抢 30 ms）：拿到构造没跑完的对象 0 次
  → 注意这个 0 不能当成「不加 volatile 也没事」。
    x86 是 TSO：store-store 不重排，HotSpot 在 x86 后端也不会把 `putfield instance`
    搬到构造体前面 —— 所以这个 bug 在 x86 开发机上「测不出来」，这正是它最坑的地方。
    JMM 允许它发生（D3 手工写出那个顺序），换 ARM / 换 JIT 版本就炸。
    判断标准只能是 JMM，不是「我跑了 50 轮没事」。

========== D3 · 把「重排后」的执行顺序手工写出来 ==========
  正常顺序：分配 → 执行构造（a=1,b=..,c=99）→ 把引用写进字段
  重排顺序：分配 → 把引用写进字段 → 执行构造
  下面这段就是把重排顺序显式写出来，看读线程会拿到什么：

  读线程在「引用已发布、构造还没跑」的窗口里抓到了：
    Singleton{a=1, b=null, c=0}
    incomplete（b==null || c!=99）= true
  → 这就是 DCL 少写 volatile 时可能递给别人的对象：引用不为 null，构造只跑了一半。
    注意 a=1 已经赋上了、b 还是 null —— 半初始化不是「全是默认值」，是「停在中途」。
    调用方拿到它之后调 b.length() 就是 NPE —— 堆栈指向调用方，跟构造毫无关系，
    所以这类 bug 的排查方向天然是错的（会去查 b 为什么是 null，而不是查单例怎么发出去的）。

========== D4 · 用 Unsafe.allocateInstance 直接看「没跑构造的对象」 ==========
  allocateInstance 拿到的对象：Singleton{a=0, b=null, c=0}
  incomplete = true
  → 这就是「分配了但没构造」的真实内存状态，不是比喻：字段全是零值/ null。
    也说明 JVM 的 new 在字节码里是一步（new + invokespecial），在内存里是两步。

结论：DCL 的 volatile 不是为了「让 instance 可见」这么模糊的一句话，
      而是为了禁止 `instance = new Singleton()` 内部「发布引用」与「初始化字段」的重排。
