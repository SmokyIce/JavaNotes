## 六条实测结论
1. 挑人是**四级链**（`DefaultListableBeanFactory:1633-1655`）：`@Qualifier` 先缩候选 → `@Primary`（1635）
   → `@Priority`（1639）→ 名字匹配（1642）→ `resolveNotUnique`（1369）。
2. **`@Autowired` 不是纯按类型**：多候选时按字段名回退 —— 字段名 `wechatChannel` + 零注解 → 注入 `wechat`。
3. `@Primary` 在名字**之前**：同样字段名，加 `@Primary` 就变成 `preferred`。
4. 两种注解的报错不同：`@Resource(name="channel")` 不存在 → `No bean named 'channel' available`（**不查类型**）；
   默认名（字段名）不存在 → 退回按类型 → 与 `@Autowired` 同一个 `NoUnique`（源码 `autowireResource:546` 的条件）。
5. **`Map` 不按 `@Order`**：`List` = `wechat→alipay→unionpay`，`Map` key 顺序 = 注册顺序（源码 Map 分支无排序）。
6. **集合不是兜底**：`required=true` 的 `List` 零候选照样抛 `expected at least 1 bean`；
   `required=false` 给的是 **null**，不是空集合。

## 踩坑（4 条）
1. 「零候选的集合注入给空集合」是先写文案后跑 → 三段全错。`resolveMultipleBeans` 空候选 `return null`，
   掉回单值分支照样 `raiseNoMatchingBeanFound`。**结论必须是 `required` 决定，不是类型决定。**
2. 注入失败死在 **`refresh()`** 不是 `getBean`：第一版 `try/catch` 包错位置，程序直接退出。
   改 `failOf(...)` 只包 `refresh()`。
3. JUL logger 名猜错：按父类 `AbstractApplicationContext` 设 `Level.OFF` 无效，
   真名是子类 `AnnotationConfigApplicationContext`（字段是 `LogFactory.getLog(getClass())`）；
   靠枚举 `LogManager.getLoggerNames()` 查出来。
4. 只打 root cause 会丢信息：`No default constructor found` 在中间层 `BeanInstantiationException` 上。
