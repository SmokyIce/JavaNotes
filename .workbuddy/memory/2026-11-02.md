## 关键结论（写进笔记 + 题库 Q19/Q20）
- 捕获 = 值拷贝，证据是合成方法 `lambda$sectionB$1(int, int)` 的第二个形参；字段能改是因为捕获 `this`（合成方法非 static）；`int[]` 绕过是因为拷引用。
- `for` 编译错、`for-each` 拿 `[1,2,3]`、数组绕过拿 `[3,3,3]`。
- 非捕获 lambda 复用单例（`==` true），捕获的每次新建（`==` false）→ 别当 Map key。
- 装箱：不逃逸 2.0 倍（10.0 vs 4.9 ms），逃逸 36 倍（23.7 vs 0.7 ms）。
- lambda 是 `invokedynamic` + 隐藏类，磁盘上不多一个 `.class`；`BootstrapMethods` 指向 `LambdaMetafactory`。

## 踩坑
- javac 分阶段：attribution 失败会让 FLOW 分析整个跳过，`effectively final` 错误**不报**。六条错只出五条。
- `Function.identity()` 无入参推不出 `T`，要写 `Function.<Order>identity()`。
- `static` 方法里不能用 `this.delta` —— 正好印证「lambda 的 this 属于所在方法」。

## 关键结论（写进笔记 Day 5 + 题库 Q21/Q22）
- 中间操作只记账；真跑起来是「一个元素走完全链」。判断看返回值是不是 `Stream`。
- `sorted` 不一定是屏障：`rangeClosed` 的 spliterator 自带 `SORTED`（`Streams.java:119`），
  `SortedOps.java:136` 直接 `return sink` → 空操作。实测探测 1 个 vs 换无序源 5 个。
- `count()` 在 SIZED 流上走快速路径，**整条管道连 `peek` 一起跳过**（0 条日志 vs 加 filter 后 3 条）。
- 流只能用一次；字段缓存流 = API 设计事故；正解 `Supplier<Stream>`。
- parallel：20M 求和 20→6 ms；1k 元素 ×30 轮 21→49 µs（**反向慢**）；2M×30 轮 34→5 ms。
  `parallel().forEach` 实测乱序，`forEachOrdered` 才保序。

## 踩坑
- 微基准第二次栽：5M 平方和读出「串行 1 ms / parallel 0 ms」，JIT 把 sum 向量化/常量折叠了。
  换「算不出答案」的重活（每元素 30 轮乘加）+ 两档数据量才有效。
- 「sorted 一定全量」是想当然，被实测打脸后才去翻 JDK 源码 —— **贵不贵也要 fact-check**。
- `peek` 无日志不一定是没执行，先怀疑 `count()` 快速路径。
