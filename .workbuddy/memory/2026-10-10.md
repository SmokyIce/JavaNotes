## 深挖：并发 put 丢的是 size 还是数据？（学员提问驱动）

学员问：「并发时 put 丢失的是 size，数据也同时丢，还是有可能只丢数据或只丢 size？」

**结论：三种都可能 —— `size` 和真实数据是两个独立的量，两个方向都会偏。**

**根因（JDK 8 `putVal` 顺序）**

```java
tab[i] = newNode(hash, key, value, null);   // 第一步：节点写进桶
...
++size;                                     // 第二步：计数器 +1
```

两步之间无原子性保证：

- 情形 A：两线程写**不同桶** → 数据都进去（+2），但 `++size` 撞车（+1）→ **只丢 size**，偏差为**正**
- 情形 B：两线程写**同一空桶** → 数据被覆盖（实际 +1），但两次 `++size` 都成功（+2）→ **只丢数据**，偏差为**负**
- 情形 C：并发 `resize` → 双份新数组互相覆盖，大批数据消失

## 改动

`day2/HashMapBuAnQuan.java` —— 加了第二口径统计：

## 追加：JDK 8 是否已避免成环？—— 实测推翻常见说法

学员问：「JDK 8 现在是否已经避免成环了？」

**结论：没有完全避免。JDK 8 把成环从「必然」降成了「偶发」。**

**新增代码** `HashMapBuAnQuan` 里的环检测：

- `jianCeHuanShu()` —— 反射读 `table`，对每个桶检测
- `youHuan()` —— **Floyd 快慢指针**（O(n) 且无需猜上限）
- `quNext()` / `zhaoNextZiDuan()` —— 沿继承链找 `next` 字段
  （必须沿继承链，因为树化后节点是 `TreeNode`，`next` 声明在父类 `Node` 里）
- 复用同包 `HashMapProbe.tableOf()` / `REFLECT_OK`（package-private 可直接访问）
- main 里给每个 put 线程加 try-catch + `AtomicInteger bengKuiShu`，统计崩溃线程数

**实测（JDK 17.0.12，8 线程 × 5000，共 13 次）**

| 结果 | 次数 |
| :--- | --: |
| 无环、但数据照样丢一万多 | 11 |
| 检出 2 个桶成环 | 1 |
| 直接死循环，超时杀进程 | 1 |

约 **15%** 概率踩到结构损坏。**这修正了"JDK 8 已修复成环"的流行说法。**

**为什么还会成环（根因）**

`resize()` 里 `table = newTab` 在搬运**之前**执行：

```java
Node<K,V>[] newTab = (Node<K,V>[])new Node[newCap];
table = newTab;          // ← 先挂上去
if (oldTab != null) { ... 才开始搬运 ... }
```

两线程同时 resize：A 挂上 newTabA 后，B 读 `table` 拿到的就是 newTabA，
于是 **A 在往 newTabA 写、B 把 newTabA 当源在读**，同一条链被一边写一边读 → 能拼出环。

JDK 8 真正修掉的是 JDK 7 那个**必然发生**的自环（头插 `e.next = newTable[i]` 反转顺序
+ 缓存 `next`，两线程交错几乎必然成环），改成尾插 + `loTail.next = null` 断尾后单线程不出错。

**第三类故障（新发现）**：并发树化

最狠的一次 8 个线程**全部**抛异常退出，40000 条只进去 1542：

```text
java.lang.ClassCastException: class java.util.HashMap$Node
    cannot be cast to class java.util.HashMap$TreeNode
    at java.util.HashMap$TreeNode.moveRootToFront(HashMap.java:1986)
    at java.util.HashMap$TreeNode.putTreeVal(HashMap.java:2165)
    at java.util.HashMap.putVal(HashMap.java:636)
```

桶内链表到 8 个要树化时，另一线程在同桶 `put` 读到「半转换」状态 → 强转炸。
已把这句写进类头注释的「情形 D」。

**三类故障汇总**：数据丢失（几乎每次）/ 成环（~15%）/ 并发树化（偶发但全崩）。

## 追加：扩容的两条触发路径（学员提问驱动）

学员问：「什么情况下 16 会变为 32、32 变为 64？」

**答案有两条路径**，第二条大多数人不知道：

| # | 触发条件 | 时机 |
| :-- | :--- | :--- |
| ① | `++size > threshold`（= 容量 × 0.75） | 16→第 13 个；32→第 25 个；64→第 49 个 |
| ② | 桶内链表变长 **且 容量 < 64** | `treeifyBin()` 第一行：`if (tab.length < MIN_TREEIFY_CAPACITY) resize();` |

`MIN_TREEIFY_CAPACITY = 64`，所以「链表到 8 个就变红黑树」**不完整**：
容量 < 64 时走的是扩容，容量 ≥ 64 才真树化。

**新增** `day2/HashMapKuoRong.java`：用 `hashCode()` 恒为 0 的 `ChongTuKey` 制造极端冲突，
让「桶内链表长度 == size」，两个触发条件先后出现。

**实测（JDK 17.0.12）**

```text
第 8 个   容量 16   阈值 12
第 9 个   容量 32   ← 16→32 ｜ 链表触发（size 才 9，远没超阈值 12）
第 10 个  容量 64   ← 32→64 ｜ 链表触发（size 10 也没超阈值 24）
第 11 个  容量 64   （已到 64，转为树化）
第 49 个  容量 128  ← 64→128 ｜ size 49 > 阈值 48，这才是 size 触发
```

**反直觉点**：学员问的那两个变化，在这个实验里**都是链表触发的**，跟 size 完全无关。
key 分布均匀时才走「第 13 / 25 个」那条路。

**同步更新**：`day2-kuorong-result.txt`（快照）、`README.md`（新增「Day 2 补充实验 1：扩容的两条触发路径」
小节 + 目录树补 3 个新文件）、`W01-Java集合.md`（Day 2 知识点末尾插入「扩容其实有两条触发路径」含源码依据 + 实测表）。

## 追加：扩容时桶 0 的元素去哪？（学员提问驱动）

学员问：「桶 0 到桶 15 变成桶 0~31 时，桶 0 上第 9 个元素会跑到桶 16，还是继续挂在桶 0？」

**答案：取决于这个元素自己的 hash 在「新增那一位」上是 0 还是 1**，跟它是第几个元素无关。

规则：`hash & oldCap` → 0 留原下标（lo 链）；非 0 移到 原下标 + oldCap（hi 链）。

**新增** `day2/HashMapChaiLian.java`，两个实验：

- 实验 A：4 个 key，hash 取 `0x00/0x10/0x20/0x30`（低 4 位全是 0）
  → 容量 16 时全在桶 0；扩容到 32 后 **k0/k2 留桶 0，k1/k3 去桶 16**（桶 0 被劈成两条链）
- 实验 B：`hashCode` 恒为 0 的 key 塞 11 个
  → 容量 16→32→64 一路涨，元素**始终在桶 0，一个都没拆**
  因为扩容不改变 hash，只让更多位参与运算；hash 高位全是 0 → `(n-1) & 0` 永远 0

**关键澄清**：不是「第几个元素」决定去向，是「每个元素自己的 hash」决定——
桶 0 里第 9 个和第 1 个地位完全一样。想让同桶元素被拆开，前提是它们的 hash 在那一位上有差异。

## 追加：hash 存哪 / 扩容要不要梳理链表 / 容量上限（学员连环提问）

学员连问三个递进问题，都答了并做了实测。

**Q1「不是说不用再算一遍吗，那桶 0 的链表还要重新梳理吗？」**

答：**要梳理，但不重算**——两件事说的是不同层面。

| 动作 | 扩容要做吗 |
| :--- | :--- |
| 调 `hashCode()` / 扰动 / 用新容量取模 | ❌ 不用 |
| 遍历链表 + 重新串指针（拆 lo/hi 两条链） | ✅ 要做 |

关键：`Node` 里有 `final int hash` 字段（存的是扰动后的值），扩容直接 `e.hash & oldCap` 读一位。
对比 JDK 7 的 `indexFor(e.hash, newCapacity)` —— 要用新容量重新取模。
**省的是「算」（hash + 取模），省不掉「搬」（遍历 + 串链）**，拆链是 O(n)。

**Q2「桶里挂的对象存了哈希值，直接比较就行了？」**

答：是，而且 `Node.hash` 有**两个用途**：
1. 扩容拆链：`e.hash & oldCap`
2. **加速 key 比较**：`if (e.hash == hash && ((k = e.key) == key || key.equals(k)))`
   —— 先比 hash（一次整数比较，便宜），hash 相同才调 `equals`（可能很贵）。
   大多数情况 hash 就不同，`equals` 被短路掉。
   但**hash 相同 ≠ 同一个 key**（那是哈希冲突），`equals` 不能省。

**Q3「哈希值是 32 位，那最多可以扩容到 2 的 32 次方个桶吗？」**

答：**不是 2^32，上限是 2^30**（`MAXIMUM_CAPACITY = 1 << 30` = 1073741824）。

原因：容量必须是 2 的幂，而桶数组长度是 `int`，`1 << 31 = Integer.MIN_VALUE`（负数）当不了长度，
所以 2 的幂里最大的安全值是 `1 << 30`。到顶后 `resize()` 把 `threshold` 设为 `Integer.MAX_VALUE`，不再扩容。

**新增** `HashMapKuoRong` 实验 C，实测：

```text
HashMap.MAXIMUM_CAPACITY = 1073741824
new HashMap<>(100)                 → 128
new HashMap<>(1000)                → 1024
new HashMap<>(1073741823)          → 1073741824
new HashMap<>(Integer.MAX_VALUE)   → 1073741824   ← 被截断
```

（用 `new HashMap<>(超大值)` 读 threshold 验证——构造时**不会分配数组**，懒加载，所以安全。）

`W01-Java集合.md`（插入「hash 存在哪 / 同一个 hash 的第二个用处 / 容量的天花板」三小节，
含源码片段 + 实测表 + 「容量 2^30 时只用低 30 位、最高 2 位闲置」的延伸点）。

**关键实测数字（JDK 17.0.12）**

- `contains`：ArrayList **375,924 ns/次** vs HashSet **209.9 ns/次** → **1791 倍**
- 去重：只写 hashCode → size=**2**；只写 equals → size=**2**；都写 → **1**（两种失败方式不同）
- 迭代：HashMap **749,910 ns/轮** vs LinkedHashMap **35,350 ns/轮** → **21.2 倍**
  （30 万删到 1 千后 capacity 仍是 **524288**，HashMap 每次要白扫 52 万个 null 桶）
- 内存：HashMap **76.7 B/元素**、LinkedHashMap **84.8 B/元素**，差 **8.1 B**（理论 8 B 压缩指针）
- LRU：容量判断写成 `>=` 只留住 **2** 个（`removeEldestEntry` 是在新元素插入**之后**才调用）

**三个反直觉点（学员这类人吃这个）**

1. HashSet 装 1..12 打印是**升序** —— `Integer.hashCode()` 返回自身、容量 16 时 `n & 15 == n`。
   换字符串立刻乱；容量 16 与 64 的顺序完全不同。**「无序」≠「随机」**。
2. 遍历中 remove 一个**不存在的元素不抛 CME** —— `modCount` 只在真的改到结构时才 +1。没报错 ≠ 安全。
3. **更重的 LinkedHashMap 迭代反而快 21 倍** —— HashMap 迭代器要扫完整个 table（含 null 桶），
   O(capacity + size)；删元素不缩容。内存开销和遍历性能是两笔独立的账。

**踩坑记录（可复用）**

- **嵌套静态类不能用 `final`**：`ZuHe` 声明成 `static final class` → 三个子类编译报
  「无法从最终 ZuHe 进行继承」。想给子类继承的基类不能 final。
- **javac 的中文报错在 Git Bash 下是 GBK 乱码**，`-J-Duser.language=en` 也压不住。
  最快的定位方式是**看 `文件:行号: 错误:` 的行号**，别在乱码文案上耗时间。
- **Java 字符串/注释里的英文双引号会截断源码**：写「把它"弄丢"了」这种中文引号时，
  要用 `「」`，否则 `"它在集合里，只是被"弄丢"了"` 直接编译失败。
- **核对 JDK 源码的正确姿势**（比搜网页权威）：
  ```bash
  mkdir -p /tmp/jdksrc && cd /tmp/jdksrc
  jar xf "/c/Program Files/Java/jdk-17/lib/src.zip" java.base/java/util/HashSet.java
  ```
  注意 zip 里的条目前缀是 **`java.base/`**（直接写 `java/util/HashSet.java` 会抽不出来，还静默不报错）。
  本节所有 HashSet/LinkedHashMap 源码行号都据此核对过。
